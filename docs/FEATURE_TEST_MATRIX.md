## 1. 目的与原则

本文档是插件的功能目录、测试边界和执行记录。功能清单以实际 UI、后台消息协议、content script、shared 模块和现有自动化测试交叉确认，不以旧 PRD 中尚未实现的规划项冒充已交付能力。

每个已实现功能都有独立编号。每个编号至少需要三类证据：

1. 静态/单元或 flow contract 检查：验证规则、状态转移、消息协议和安全门禁。
2. 浏览器独立场景：一次只验证一个功能，使用 ego-browser 观察实际页面、面板和日志。
3. 边界或回归结论：记录正常路径、异常输入、刷新/重载、重复操作或平台页面变化下的结果。

涉及真实 BOSS 沟通的场景遵守最小副作用原则：默认使用页面诊断、扫描预览和受控的 1 份测试；只有明确需要验证真实发送回执时才实际发送，并将本次上限调为 1。不会自动点击 BOSS 原生“发简历”按钮，也不会尝试验证码、平台限流或风控绕过。

## 2. 状态定义

| 状态 | 含义 |
|---|---|
| `待测` | 已列入范围，尚无本轮独立浏览器证据 |
| `通过` | 单元/flow、浏览器场景和边界检查均通过 |
| `问题` | 已发现可复现问题，需记录根因、修复和回归证据 |
| `阻塞` | 需要用户登录、验证码、平台临时限制或外部状态，不能安全绕过 |
| `不适用` | 该能力明确不在当前版本或产品边界内；保留边界测试记录 |

“单测/冒烟”列填写对应命令、测试名称或待补测试；“浏览器场景”必须是一个独立场景，不把多个功能的通过结果合并填入一个编号。

## 3. 自动化基线

| 层级 | 命令 | 当前基线 |
|---|---|---|
| 单元测试 | `npm test` | 139 个 unit tests + flow contract tests |
| 冒烟测试 | `npm run smoke` | 通过 |

| 浏览器 | ego-browser + 本矩阵 | 本轮逐项补录 |

基础回归每次修复后必须重新运行 `npm test && npm run smoke`。真实页面测试发现问题时，先在 `dev` 修复，再重新执行受影响编号和基础回归。

## 6. 执行顺序

按以下顺序执行可降低真实副作用：

1. `ENT-*`：入口、连接、版本和面板基础。
2. `FIL-*`、`SRC-*`：先用扫描预览验证规则、求职期望和来源恢复。
3. `DATA-*` 中不发送消息的配置、日志和历史场景。
4. `MSG-*`、`RES-*`：先在面板和规划层验证，最后才做最多 1 份真实发送回执。
5. `RUN-*`、`LAY-*`：在本次上限为 1 的条件下验证控制、执行隔离和刷新保护。
6. `SCOPE-*`：记录边界，防止把规划项当成回归失败。

每个编号完成后立即填写状态和证据；发现问题时新增“复现步骤、实际结果、根因、修复提交、回归编号”，修复后不得只依赖单测通过。
