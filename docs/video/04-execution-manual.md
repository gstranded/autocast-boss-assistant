## 3.5 演练实测结论（2026-08-15 凌晨）

- ✅ **完整链路已真实跑通**：扫描 195 岗 → 通过 1 → 投递一份 → 创建消息页 → 触发沟通（HR=林先生/二进一）→ 会话匹配 → 第 1/2 段消息**真实发送成功** → `success（1/1）` → 「成功投递 1 份，跳过 0，失败 0」
- ✅ 演示视频已产出：`docs/video/boss-haitou-demo.mp4`（221s，1920x1050，H.264，6.6MB）
- ⚠️ 关键环境前提（ego lite）：
  1. **SW 默认窗口漂移**：每次 SW 重启后 `chrome.tabs.create` 的默认窗口可能变化（曾见 1333624023/1333623972），投递前必须把列表 tab `chrome.tabs.move` 到 SW 默认窗口（否则报 `Tab opener must be in the same window`）
  2. **runner 卡死**：中断的任务会让 SW 内存 runner 停在 running/pause，必须从 `chrome://extensions` 点「重新加载」彻底重启 SW（面板 reload 不够）
  3. **面板 iframe 状态残留**：面板关闭不销毁 iframe，重开复用旧状态；需要 `location.reload()` 或 F5 页面
  4. **多个 jobs tab 干扰**：列表页 tab 只能保留一个，扩展按 listTabId 定位
- ⚠️ 产品侧注意（真实用户也可能遇到）：BOSS「HR 活跃=未知」会排除已多次沟通的 HR；`{匹配技能}` 变量无法解析时扩展安全拦截（日志：模板变量渲染失败）；「发简历」按钮缺失时会暂停（安全设计）

## 4. 演练发现的环境要点（ego lite 特有，必须遵守）

1. **多窗口 opener 问题（关键）**：ego lite 的 service worker 创建消息页 tab 时使用「SW 默认窗口」（本机实测为 1333624023），若职位列表 tab 在其他窗口，会报 `Tab opener must be in the same window as the updated tab`。
   - **修复**：投递前先把列表页 tab `chrome.tabs.move` 到 SW 默认窗口。
   - **录制前检查**：`chrome.windows.getAll` + 测试 `chrome.tabs.create({openerTabId: listTabId})`。
2. **面板是 iframe（OOPIF）**：需 `Target.attachToTarget` 到 sidepanel iframe 的 target 再 `Runtime.evaluate`；每次页面重载后 targetId 会变，需重新查找。
3. **扫描会滚动加载岗位**（最多 100+ 岗），期间**不要切换/重载列表页 tab**，否则「操作超时（岗位定位/发消息）」。
4. **模板变量安全机制**：`{匹配技能}` 等变量无法解析时扩展会**阻止发送并暂停**（日志：模板变量渲染失败）。演示模板建议只用 `{HR称呼}` `{职位名称}` `{工作城市}`（有兜底值）。
5. **连续失败 3 次自动暂停**：任务会进入「已暂停」需手动「停止」→ 重新扫描。
6. **测试号多次沟通后 BOSS 侧可能不再创建新会话**（CONVERSATION_NOT_FOUND：列表侧可能已点过沟通）；正式录制前用「记录」页清空历史或换新测试号。
